# legion-toolkit

Spec sheet. Written 2026-09-06, build starts 2026-09-07.

## What it is

LEGION-STANDARDS.md as installable packages. One Yarn 4 monorepo, one rule
engine, three consumers: a lint plugin that runs under oxlint and ESLint, an
audit CLI that produces the repo scorecard mechanically, and two config
packages that complete the set. Public on npm and GitHub, MIT, copyright
Veracium LLC.

The standards doc already says why: a rule that only lives in a document
drifts (section 8.1, the 2026-08-04 incident). Today the enforcement is
copied by hand per repo, in two different shapes (howdy's
`eslint-rules/legion-rules.mjs`, legion-core's `scripts/check-legion-rules.mjs`),
and most repos have neither. This replaces both with `yarn add -D`.

## Goals

1. Every mechanically checkable rule in LEGION-STANDARDS.md and
   REACT-PARTNERSHIP.md exists as a lint rule, written once.
2. The plugin runs under oxlint (`jsPlugins`) and under ESLint v9+ with no
   code change, because oxlint's plugin API is the ESLint API.
3. `legion-audit` run in any repo reproduces the gate table from the
   hand-written Howdy audits, plus per-rule counts, PR hygiene, and test
   coverage, as markdown and JSON, with an exit code CI can use.
4. Zero runtime dependencies in every published package. oxlint, eslint,
   and typescript are peers. This keeps the packages portable through any
   corporate registry proxy and makes license review trivial.
5. Publishing is boring and verifiable: GitHub Actions only, npm provenance
   on every version, changesets for versioning.

## Non-goals (for now)

- The Next.js seed / `create-legion-app`. It consumes everything here and
  can come later.
- Type-aware rules. oxlint's JS plugin API does not support them yet, and
  none of the rules below need type information.
- A web UI or dashboard. `legion-audit` writes files; anything that renders
  them is a separate project.
- Autofixes. Reporting first. Fixes for the mechanical rules (comments,
  `React.FC`, `enum`) can come after the rules have run on real repos.

## Package: legion-rules

The engine. Each rule is an ESLint-format rule object (`meta`, `create`)
operating on the ESTree/TSESTree AST, exported individually and as a map.
Nothing here imports ESLint or oxlint; it only uses the `context` API that
both provide.

Every rule ships. Some are mechanical with no realistic false positives,
some are heuristics for the harder standards; the difference is a note in
the rule's docs, not a tier. Which level each runs at is a property of the
config, not the rule (see Tolerance levels).

### Tolerance levels

Every rule is configured with one number, 0 to 3.

| Level | Meaning                                                                              | Compiles to                                                             |
| ----- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 0     | off                                                                                  | linter `off`                                                            |
| 1     | warns, does not fail lint                                                            | linter `warn`                                                           |
| 2     | fails lint; a scoped, explained disable directive is honored                         | linter `error`                                                          |
| 3     | fails lint; no exceptions, a disable directive naming the rule is itself a violation | linter `error` plus the rule's name in `scoped-disables`' `locked` list |

Levels 0 to 2 are the severity numbers ESLint and oxlint already use, so
the config compiles to the linters' native format with no translation.
Level 3 is enforced by `scoped-disables`, which sees every directive
comment and reports any that names a locked rule. It refuses to be
disabled itself the same way. The remaining hole, a file-wide
`/* eslint-disable */` or `/* oxlint-disable */` that suppresses every
rule in the file including `scoped-disables`, cannot be caught by any
lint rule: both linters filter reports inside a disabled range before a
rule's output is seen. It is closed by `legion-audit directives`, a fast
subcommand that scans source for file-wide directives with a fixed regex
and exits non-zero on any. The recommended `lint` script is
`legion-audit directives && oxlint .`, so the check runs inside the same
`yarn lint` CI already gates on. The full audit runs the same scan.

`defineLegionConfig({ 'no-narrative-comments': 3, 'no-enum': 3,
'presentational-components': 1 })` emits the flat config or `.oxlintrc.json`
rules plus the `locked` list. Raw linter config still works for anyone who
prefers it. Defaults: `recommended` runs every rule at 2 (`no-disables` off);
`strict` runs every rule at 3 (`no-disables` at 1). There is no grading of
rules: all of them ship, and the level is the only knob.

### Mechanical rules

| Rule                              | Standard                      | What it flags                                                                                                                                                                                                                                                                    |
| --------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `no-narrative-comments`           | section 13                    | Any comment except tool directives. Port of howdy's rule with a wider built-in allowlist and two options (below).                                                                                                                                                                |
| `scoped-disables`                 | section 13, REACT-PARTNERSHIP | A disable directive that is file-wide, names no rule, carries no `-- reason`, or names a rule in its `locked` option (tolerance 3). The one-time bypass is allowed at level 2; an unscoped, unexplained, or locked one is not.                                                   |
| `no-disables`                     | REACT-PARTNERSHIP             | Every disable directive, legal or not. Visibility rule: at level 1 every honored bypass appears as a warning in lint output on every run. `strict` runs it at 1, `recommended` at 0.                                                                                             |
| `no-react-fc`                     | section 0.4, 2                | Type annotations `React.FC`, `FC`, `FunctionComponent`, `React.FunctionComponent`.                                                                                                                                                                                               |
| `no-enum`                         | section 0.4, 2                | `TSEnumDeclaration`, including `const enum` and `declare enum`.                                                                                                                                                                                                                  |
| `guarded-context-hook`            | section 4                     | A `useContext(...)` call anywhere except inside a function named `use*` whose body contains a `throw`. Also flags a raw `useContext` call being exported or returned without the guard.                                                                                          |
| `no-client-globals-in-state-init` | section 1 (hydration)         | `window`, `document`, `localStorage`, `sessionStorage`, `navigator` referenced inside a `useState(...)` argument, including a lazy initializer body.                                                                                                                             |
| `no-use-client-in-page`           | section 0.6, 3                | A `'use client'` directive in `page.tsx` or `layout.tsx` under `app/`.                                                                                                                                                                                                           |
| `no-function-keyword`             | section 0.4, 7                | Any `FunctionDeclaration` or `FunctionExpression`. Skips generators and functions whose body references `this`, the two things an arrow cannot be. Message shows the `const name = (...) => {}` form, and the `const Page = ...; export default Page;` form for default exports. |

Ternaries (section 7, none anywhere) are config, not a custom rule: oxlint
and ESLint both ship core `no-ternary`. `strict` runs it at 3,
`recommended` at 2. `no-unneeded-ternary` and
`unicorn/prefer-logical-operator-over-ternary` ride along for the messages
that point at `??`. `typescript/prefer-nullish-coalescing` (flags `||`
where `??` is meant) is included only when the consumer has oxlint's
`typeAware: true`, since it needs type information.

#### Comments: the allowlist, the options, and the bypass

Section 13 says zero comments, and the one thing it carves out is tool
syntax. The built-in allowlist is exactly that and nothing else:
`eslint-disable*`, `eslint-enable*`, `oxlint-disable*`, `oxlint-enable*`,
`biome-ignore`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`,
`@jest-environment`, `@vitest-environment`, `istanbul ignore`, `c8 ignore`,
`v8 ignore`, `prettier-ignore`, `/// <reference`, `NOSONAR`, bundler magic
comments (`webpackChunkName` and friends), and `@__PURE__` / `#__PURE__`.

Two options for codebases that sit behind another tool with its own
opinions (SonarQube is the known case: S108 and S1186 treat an empty block
or function as a defect unless it contains a comment explaining why):

- `allowPatterns: string[]`, extra regexes matched against the normalized
  comment text. A repo can add whatever its scanner demands without
  touching the rule.
- `allowInEmptyBlocks: boolean`, default `false`. When true, a comment that
  is the sole content of an otherwise empty block or function body is
  allowed. This is the narrowest shape that satisfies Sonar, and it is off
  by default because the standards say an empty block should not exist
  in the first place.

The bypass itself is mechanical, not conversational. "Skip my rules this
one time" becomes a `// oxlint-disable-next-line legion/<rule> -- <reason>`
(or the `eslint-` form), and only for rules at tolerance 2. `scoped-disables`
enforces the shape: next-line or single-line only, at least one named rule,
a reason after `--`, and none of the named rules locked at level 3.
`legion-audit` counts every disable directive and every `NOSONAR` per rule
and lists them, so bypasses are a visible number in the scorecard instead
of a thing that happened once in a chat. A `legion/*` rule set to `off` in
a repo's config is reported the same way.

#### `any` and `unknown`

`unknown` is never flagged by anything here. It is the house answer at
I/O boundaries and in `catch`, and `strict` already types catch variables
as `unknown` (`useUnknownInCatchVariables`). The `any` restriction
(section 0.3, 2) is config, not a new rule: `typescript/no-explicit-any`
as `error`, with overrides turning it off for boundary paths the consumer
declares (`lib/supabase/**`, `**/*.d.ts`, `types/db.ts` by default). The
message text points at `unknown` plus narrowing.

Component line cap (section 1, 180 lines) is not a custom rule. The
shareable config sets core `max-lines` to
`['error', { max: 180, skipBlankLines: true, skipComments: true }]` for
`**/*.tsx`, off for test files. oxlint implements `max-lines` with both
`skipBlankLines` and `skipComments` (pedantic category, off by default, so
the config must enable it explicitly). The equivalence test covers it.

| `no-literal-conditions-in-jsx` | section 1      | A comparison against a string literal used as a JSX conditional (`{slug === 'x' && ...}`).                                                                                                                                          |

| `no-manual-memo`               | React Compiler | `useMemo`, `useCallback`, `memo()` anywhere. Off unless `reactCompiler: true`, which turns it on at the config's highest level; `presentational-components` then says "drop it, the compiler memoizes" instead of "move it".        |

### Shareable configs

`legion-rules` exports `defineLegionConfig` and two presets built with it,
`recommended` and `strict` (levels above), each carrying the `max-lines`
wiring, the `no-explicit-any` boundary overrides, and the test file
overrides. `eslint-plugin-legion` re-exports them as flat configs.

### Testing

Every rule has valid and invalid cases run through ESLint's `RuleTester`
(ESLint is a devDependency of the workspace, not of any published
package). Fixtures in `fixtures/` are shaped after real code in commander,
howdy, and poker-defense, rewritten so nothing is copied verbatim. A second
test runs the built plugin through oxlint against the same fixtures and
diffs the diagnostics, so the two runtimes are proven equivalent in CI.

## Package: eslint-plugin-legion

Thin. Imports `legion-rules`, exposes the ESLint plugin shape
(`{ meta, rules, configs }`). Named by the ESLint convention so
`plugins: { legion }` resolves anywhere.

Consumption:

```jsonc
// .oxlintrc.json
{
  "jsPlugins": ["eslint-plugin-legion"],
  "rules": { "legion/no-narrative-comments": "error" },
}
```

```js
// eslint.config.mjs
import legion from 'eslint-plugin-legion';
export default [legion.configs.recommended];
```

Peer dependencies: `eslint >= 9` optional, `oxlint >= 1.53` optional
(1.53.0 shipped the JS plugins alpha on 2026-03-11; legion-core's `^1.47`
needs a bump when it adopts the plugin). A
README section explains that under oxlint the plugin API is alpha, which
behaviors are verified in CI, and that ESLint is the fallback if a rule
misbehaves.

## Package: legion-audit

A CLI, `legion-audit`, run from a repo root. Read-only. It runs the gates,
runs the lint rules through whichever linter the repo has (or a bundled
oxlint config if it has none), and writes `AUDIT.md` and `audit.json`.

### Checks

| Check                  | Source of truth                                                                                | Output                                |
| ---------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------- |
| Typecheck              | `tsc --noEmit` per workspace                                                                   | pass/fail, error count                |
| Lint                   | repo's `lint` script if present, else `oxlint -c <bundled> --format json`                      | pass/fail, counts per `legion/*` rule |
| Tests                  | repo's `test:ci` or `test` script                                                              | pass/fail, suites, tests              |
| Format                 | `prettier --check` if prettier is present                                                      | pass/fail                             |
| Comment count          | plugin diagnostics                                                                             | count, files                          |
| Bypasses               | disable directives, `NOSONAR`, `legion/*` rules set to `off`                                   | count per rule, file:line, reasons    |
| File-wide disables     | regex scan for `/* eslint-disable */` and `/* oxlint-disable */` with no rule list             | hard fail, file list                  |
| Component line cap     | plugin diagnostics or own count                                                                | count, worst offenders                |
| PR hygiene             | `git log -n 80 --format=%s`, count messages matching `(#\d+)`                                  | ratio, last PR-tagged commit and date |
| Test coverage by file  | every `components/**/*.tsx` and `hooks/use*.ts` expects a sibling or `__tests__` `.test.` file | missing list                          |
| Package manager sanity | exactly one lockfile                                                                           | pass/fail                             |
| Dependency audit       | `yarn npm audit --severity high` or `npm audit --audit-level high`                             | pass/fail, count                      |

### Output

`AUDIT.md` mirrors the shape of the hand-written audits: a gate table at the
top, then per-rule counts with file:line, then the hygiene sections. No
letter grade. The grade in the hand audits is judgment, and the tool should
not pretend otherwise. It computes a numeric score from a documented
formula so runs are comparable, and the narrative stays with the human.

`audit.json` has the same data. `legion-audit --baseline audit.json` diffs
against a previous run and exits non-zero on any regression, which is the
CI use.

Flags: `--json`, `--md`, `--baseline <file>`, `--fail-on <regression|error|never>`,
`--workspaces` (auto-detected from yarn/pnpm workspaces).

Subcommands: `legion-audit` (full run), `legion-audit directives` (the
file-wide disable scan only, fast, for use inside a `lint` script).

### Constraints

Zero runtime deps. Child processes for `tsc`, the linter, the test runner,
`git`, and `prettier`. Parsing of lint output is JSON only, never scraped
text. If a tool is missing the check reports `skipped`, never `pass`.

## Package: legion-steer (day two)

Lint catches a violation after the agent has already written it. By then
a 600-line component exists and the fix is a refactor the user never
asked for. `legion-steer` moves the rules earlier: into the agent's
context before it writes, and into the write itself.

### `legion-steer init`

Writes a managed block (start and end markers, idempotent) into
`AGENTS.md` and drops one-line pointer files for tools with their own
convention: `CLAUDE.md` (`@AGENTS.md`), `.junie/guidelines.md`,
`.cursor/rules/legion.mdc`, `.github/copilot-instructions.md`. `--targets`
selects which. Never overwrites content outside the markers.

The block is generated from the resolved lint config, never hand-written:
the rules that are on, each at its level, one line of how to comply, the
component cap, the bypass syntax and which rules are locked, and the
`lint` command. A rule the config does not enforce cannot appear in the
block, so the steering cannot drift from the enforcement. The block
points at LEGION-STANDARDS.md for the reasoning; it does not reproduce
it.

The block also tells the agent how to dial the toolkit in for this repo,
not only what the rules are: where the levels live
(`scripts/sync-oxlintrc.mts` and `defineLegionConfig`), what each level
means and how to propose raising one, how to declare `any` boundary paths
and comment allowances instead of bypassing, how to run `legion-audit` and
read the scorecard, and that a bypass is a `disable-next-line` with a
reason and nothing else. The goal is an agent that adjusts the
configuration through the sanctioned knobs and asks before changing a
level, rather than one that reaches for a directive.

Also registers the hooks below in `.claude/settings.json`, merging with
whatever is there.

### `legion-steer check`

Regenerates the block in memory and diffs it against the file. Non-zero
on drift. Runs in CI next to `lint`.

### `legion-steer hook`

A Claude Code hook handler reading the hook JSON on stdin.

| Event         | Matcher       | Behavior                                                                                                                                                                                                                                                                 |
| ------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `PreToolUse`  | `Write`       | For `.ts`/`.tsx` targets, runs the rules on `tool_input.content` (temp file, `oxlint --format json`). Any diagnostic at level 2 or above: exit 2, diagnostics on stderr. Exit 2 on `PreToolUse` blocks the write, so the oversized or logic-laden component never lands. |
| `PostToolUse` | `Edit\|Write` | Lints `tool_input.file_path`. Diagnostics on stderr with exit 2. Not blocking (the edit already happened) but fed straight back to the agent, one edit later instead of one task later.                                                                                  |

Diagnostics are phrased as instructions: what to move where, not just
what is wrong. The rule messages in `legion-rules` follow the same
convention, since for agents without hooks the message is the only
steering at fail time.

Limits, stated in the README: hooks are a Claude Code mechanism; other
agents get the instructions file and their own lint gate. A `PreToolUse`
hook cannot lint an `Edit` before it lands without reconstructing the
file, so edits are caught by the `PostToolUse` pass.

## Package: legion-toolkit (umbrella)

One install that grows with the repo. `yarn add -D legion-toolkit` pulls
every published package as a dependency and exposes each through a subpath
export, so a consumer never has to know the individual names:

```jsonc
// .oxlintrc.json
{ "jsPlugins": ["legion-toolkit/eslint-plugin"] }
```

```js
// eslint.config.mjs
import legion from 'legion-toolkit/eslint-plugin';
```

```jsonc
// package.json
{ "prettier": "legion-toolkit/prettier" }
// tsconfig.json
{ "extends": "legion-toolkit/tsconfig/next.json" }
```

It declares its own `bin` for `legion-audit` (a shim that imports the real
CLI) so the command exists under Yarn, npm, and pnpm regardless of how each
links transitive bins. Subpath exports are the supported path; relying on
`eslint-plugin-legion` resolving as a transitive dependency works under
Yarn's node-modules linker and npm but not under pnpm's strict isolation,
so the docs never show that.

Rule: every new package added to this monorepo is added to the umbrella's
`dependencies` and `exports` in the same PR, and a CI check fails if a
workspace package is missing from either. Changesets keeps the umbrella
version in a `linked` group with its children so it bumps whenever any of
them does.

The individual packages stay published on their own for consumers who want
a smaller footprint or a smaller thing to put through dependency review
(the plugin alone is the common case).

Installing the umbrella runs nothing. There is no `postinstall`, no tool
activates on its own: the plugin only runs where a lint config references
it, `legion-audit` and `legion-steer` only run when invoked, the configs
only apply where `extends` or `"prettier"` points at them. Turning a tool
off is not referencing it; turning a rule off is level 0 in the config.

### `legion-toolkit init` (day two)

The front door. One command that wires every tool the consumer wants, so
the umbrella never ends up installed and unreferenced.

Detects without asking: package manager (lockfile), oxlint or ESLint
(installed package and existing config), existing prettier and tsconfig,
workspaces, Next (`app/`) or RN (`expo` dependency), and which agents are
present (`.claude/`, `.junie/`, `.cursor/`,
`.github/copilot-instructions.md`).

Asks at most four questions, each with its default preselected:

1. Preset: `recommended` or `strict`, with a one-line statement of the
   difference (levels, and whether bypasses are honored).
2. Tools: lint, prettier config, tsconfig, audit script, steering. All on
   by default except any that would collide with an existing config,
   which is off by default and labeled as "extend the one you have?".
3. Boundary paths for `any`: prefilled with the defaults, editable.
4. Steering targets: preselected from the agents detected.

Then it prints the plan, every file it will create or touch, as a diff for
existing files, waits for a yes, writes, and finishes by running
`legion-audit` once so the first output the consumer sees is their repo's
scorecard as it stands.

Rules: never overwrite. An existing `eslint.config.mjs` or `.oxlintrc.json`
gets the plugin merged in; an existing prettier or tsconfig is left alone
unless chosen. Steering is delegated to `legion-steer init`, not
duplicated. `--yes` takes every default with no prompts, for CI and for
agents (an agent that hits an interactive prompt hangs). `--dry-run`
prints the plan and stops. `npx legion-toolkit init` in a repo with nothing
installed runs detection, prints the install line for the detected package
manager, and asks before running it.

## Package managers

Two different questions with two different answers.

**Contributing to this repo: Yarn 4 only.** `packageManager: yarn@4.18.0`
in the root `package.json` is the enforcement. pnpm 9+ reads that field and
refuses to run when it names a different manager (default
`package-manager-strict: true`), so `pnpm install` in a clone fails before
it touches anything. A root `preinstall` script
(`scripts/require-yarn.mjs`, checks `npm_config_user_agent`) covers npm
the same way. CI uses corepack and `yarn install --immutable`.

**Consuming the packages: Yarn, npm, and pnpm all supported, proven in
CI.** Nothing in the packages depends on the installer: subpath exports
resolve the same everywhere, the umbrella ships its own `legion-audit`
bin, and there are no runtime deps to hoist. A consumer smoke matrix in
`ci.yml` runs `npm pack` on every package, installs the tarballs into a
fixture Next app under Yarn 4, npm, and pnpm, and in each runs the plugin
through oxlint and ESLint and runs `legion-audit`. The README claims
support for exactly the three managers that matrix is green on.

## Licensing and publishing

Done once, done right, enforced by a CI check that fails if any of it
drifts.

- `LICENSE` at the repo root and copied into every package at build time.
  MIT. `Copyright (c) 2026 Veracium LLC`.
- Every `package.json`: `"license": "MIT"`, `"author": "Veracium LLC"`,
  `repository` (with `directory` for the workspace), `homepage`, `bugs`,
  `keywords`, `files` whitelist, `sideEffects: false`,
  `publishConfig: { access: "public", registry: "https://registry.npmjs.org/" }`.
- No SPDX headers in source. Section 13 forbids them and MIT does not need
  them.
- `SECURITY.md` at the root with a disclosure contact.
- `CHANGELOG.md` per package, generated by changesets.
- Publishing only from `release.yml` using npm trusted publishing (OIDC),
  `npm publish --provenance`. No long-lived npm token in the repo or on a
  laptop. A local `npm publish` is blocked by a `prepublishOnly` guard that
  checks for the CI environment.
- Fixtures are original code shaped after Legion's own public repos. No
  third-party or client code in fixtures, tests, or examples. Commit
  history and docs reference only LEGION-STANDARDS.md,
  LEGION-CODING-PHILOSOPHY.md, and Legion's own repos as sources.

### Public repo hygiene

The repo is public and accepts fork PRs. Section 12 of the standards
becomes GitHub configuration, enforced on outside contributors and on
Legion alike.

- Branch protection on `main`: PR required, CI status check required, one
  approving review required, no force pushes, rules apply to admins.
- `CODEOWNERS` with `* @Kprince1101`, so every PR requires Legion's review
  automatically.
- `CONTRIBUTING.md`: how to run `yarn validate`, PRs need a changeset, the
  comment rule and the component cap apply to contributions and are
  enforced by lint, not by review.
- `.github/PULL_REQUEST_TEMPLATE.md`: what changed, why, what was verified.
- Fork PRs get a read-only token and no secrets. `release.yml` runs only on
  tagged pushes to `main` and is the only workflow with `id-token: write`.
- Dependabot for GitHub Actions and devDependencies, weekly, grouped.
- Contributor licensing: MIT in, MIT out under GitHub's terms, no CLA.
  Outside contributions are their authors' copyright, so the LICENSE line
  reads `Copyright (c) 2026 Veracium LLC and contributors` from the first
  merged outside PR onward.

### Using it behind a corporate registry

Unscoped public packages install through any Nexus or Artifactory proxy
that fronts npmjs.org with no extra step. Zero runtime deps means there is
nothing else to allowlist. For a hosted-only registry, the release
tarballs are attached to each GitHub release so they can be pushed in by
hand, and the plugin also builds to a single-file `dist/plugin.mjs` that
can be dropped into a repo's lint config directly.
